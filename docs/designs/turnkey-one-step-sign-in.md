# Design: One-step Turnkey sign-in

Generated by /office-hours on 2026-09-27

## Problem

Turnkey email login authenticates the person, but OhMyFund then asks that person to approve a separate wallet message to create its own session. The signed-out page still says “Connect wallet” after Turnkey knows the account. Closing the message dialog leaves a raw “User canceled the signing process” error. Yann called the second signature “useless” and wants login to finish after the email step. A retained `?wallet=1` URL can also start a modal again on reload.

## Decision

- One deliberate tap on **Sign in** starts Turnkey email login. After it succeeds, OhMyFund establishes its API session without a second wallet prompt and opens Portfolio.
- Passive page visits and refreshes may restore sessions silently. They never call `handleLogin` or open a Turnkey modal.
- Copy, Create, Add asset, and Wallet taps count as deliberate sign-in intent. A one-use navigation signal may open login only as the immediate result of that tap. A refresh or pasted URL never opens it.
- Use Turnkey's signed session token as the proof presented to the API. The API verifies the token's Turnkey signature, expiry, expected organization and user claims, and that this user is authorized for the selected Solana wallet before issuing its existing HttpOnly session cookie. Keep the current wallet-challenge path for local browser-wallet development.
- The browser never treats an unverified token or local `authState` as an OhMyFund session. No token is logged or placed in a URL.

## User states

| State | What the person sees | Action |
| --- | --- | --- |
| Signed out | “Sign in” | Tap opens Turnkey email login once. |
| Turnkey login in progress | Turnkey email flow | No OhMyFund signature request. |
| Turnkey authenticated, API binding in progress | “Finishing sign-in…” | Wait; no extra tap or modal. |
| Both sessions ready | Portfolio and wallet address | Normal use. |
| Binding fails | “We couldn't finish sign-in. Try again.” and Retry | Retry the server bind; do not restart email login unless Turnkey's token expired. |
| Turnkey login canceled | Signed-out page | No red technical error. A later tap can retry. |
| Turnkey account has no Solana wallet, or several candidates | Clear account issue | Never silently choose the first wallet; offer a supported explicit choice or contact support. |

## Approaches considered

- Small UI fix: consume `?wallet=1` and improve labels, but retain the second signature. Rejected because it leaves Yann's main complaint unresolved.
- Chosen: verify the Turnkey session at the API and keep the existing OhMyFund cookie. It removes the signature prompt while preserving server-side wallet checks and existing API authorization.
- Replace all OhMyFund cookies with Turnkey tokens on every request: wider auth rewrite with no benefit needed for this fix.

## Implementation boundaries

1. Add a separate API bind endpoint for a signed Turnkey session. Do not weaken `/auth/bind` or the development-wallet challenge.
2. First prove on preview, with a real issued token, that the installed `@turnkey/crypto` `verifySessionJwtSignature` accepts it and that the signed claims identify the current user and organization. This helper checks the signature only. The API must independently check token shape, expected algorithm/header, `exp`, `iat` when present, clock skew, and a maximum accepted lifetime. Reject wrong-environment tokens and missing claims. Do not ship if the token cannot be validated safely.
3. Prove the signed token user can use the selected Solana wallet, not merely that the wallet belongs to the suborganization. Either verify a documented single-user wallet invariant against Turnkey data or check the user's wallet permission directly. Select a previously linked wallet deterministically; if several unlinked Solana wallets exist, require an explicit choice. Verify the address-to-suborganization mapping and account before issuing the cookie.
4. Treat the token as a bearer credential. Use origin checks and bounded rate limits keyed by IP and token fingerprint; never log, URL-encode, or persist the raw token on the server. State the app-cookie lifetime separately from token expiry. Turnkey signature validation alone does not prove the token is not revoked, so verify revocation if Turnkey provides an authoritative check; otherwise cap the accepted token lifetime and document the residual window. Repeated binding must not create unlimited app sessions.
5. The web client sends `tk.session.token` only to this endpoint. It may bind automatically after a completed Turnkey login or on silent session restoration. It never calls `handleSignMessage` for login. If Turnkey reports a different user than the app cookie, clear cached private data and revoke or replace the old app session before showing the new account. Do not show cached data for user A while Turnkey reports user B.
6. Logout revokes the app cookie, clears the Turnkey session, cancels pending bind requests, and prevents silent rebind from the just-ended token. If Turnkey logout fails, show a clear incomplete-logout state and let the person retry; do not present a fully signed-out state that immediately signs back in. Sync this state across tabs.
7. Remove any page-load call to `handleLogin`. Replace persistent URL login triggers with an in-memory, single-use navigation signal created by a tap; consume it before opening the modal. The requested Create, Copy, Add, or Wallet action is tracked separately with a short TTL and cleared only after completion or explicit cancellation. A reload can resume the page without replaying the login modal or an action. Use “Sign in” while signed out and an address once the app session is ready.
8. On failed binding, leave a visible Retry action and a clear error. Do not loop requests or block ordinary navigation. Canceling a Turnkey modal returns to the signed-out state without an error banner.

## Verification and release gate

- Unit and API integration tests cover malformed headers and claims, signature rejection, expiry and lifetime limits, organization and user-wallet mismatch, wrong-environment tokens, repeated bind, cookie issuance, cancellation, one-use intent behavior, logout restoration across tabs, and account switching.
- Test on a Turnkey-allowed preview origin with a real email login, on mobile and desktop: one tap, one email flow, no signature dialog, automatic Portfolio access, refresh without popup, navigation across all public pages, logout, and Retry after a simulated API failure.
- Deploy the API first. Promote the web release only after the real Turnkey preview test passes. This gate is required because a direct `signMessage` replacement previously failed in production and was rolled back.

## Open technical questions

- Confirm that the token exposed by the installed React wallet kit is accepted by Turnkey's production notarizer verifier and has the needed claims. Inspect a real token on preview without recording or sharing it.
- Confirm the authoritative Turnkey API check for the signed-in user's access to the chosen wallet, and whether an active-session or revocation check is available.
- Decide the shortest practical accepted token lifetime after measuring Turnkey's actual session lifetime. Keep the existing app cookie lifetime unless a deliberate security review changes it.

## Next step

First validate one real Turnkey session token and wallet association on preview. Then build the API and web flow, and perform one real mobile login on preview before approving production release.
