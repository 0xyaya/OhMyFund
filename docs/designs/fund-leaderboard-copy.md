## Problem Statement

New users can create a fund, but they may not know which assets or weights to choose. Thomas was asked to try OhMyFund, reached the initial basket decision, and stopped. A trusted public fund gives that user a concrete starting point without requiring them to invent a portfolio first.

## Demand Evidence

- Yann showed OhMyFund to Thomas and asked him to try it.
- Thomas did not know what to put in his initial basket and stopped.
- Yann plans to publish his own fund and write about it on X, giving the first public fund a trusted distribution path.
- This is usability evidence from one observed user, not proof of broad demand.

## Status Quo

- Every user must create a basket from scratch.
- The user must choose assets and weights before seeing value.
- Sharing currently communicates a basket, but it does not give the recipient a public fund they can copy into OhMyFund.

## Target User & Narrowest Wedge

The first target user is someone like Thomas: interested enough to try OhMyFund, but unsure how to construct a first basket. The narrowest useful release is one public leaderboard containing explicitly published funds, with a direct snapshot-copy action.

## Constraints

- Funds remain private by default. Publishing is explicit and reversible.
- The leaderboard is public to browse. Copying requires sign-in.
- Rank by copy count only. Do not rank or imply investment returns.
- A copy is an independent snapshot. Later edits to the source fund do not change existing copies.
- Copy the source asset identities and target weights into a new fund owned by the copying user.
- Never copy holdings, balances, activity, plans, or ownership metadata.
- After copying, open the new fund and offer an optional draft recurring buy.
- OhMyFund must continue to say that draft plans do not execute purchases.
- The first release uses the existing horizontal navigation and Ledger design system.

## Premises

1. The main onboarding block is choosing a first basket, not wallet connection or recurring-buy setup.
2. Trust comes from recognizing the creator and reviewing the basket, not from a performance claim.
3. Snapshot copying is safer and simpler than following future manager changes.
4. The existing fund model should remain the source of truth for both private and public funds.

## Approaches Considered

### Approach A: Extend the existing fund model

Add publication metadata and copy lineage to existing funds. Expose narrow public read endpoints and an authenticated atomic copy endpoint. This is the selected approach because it reuses fund validation, asset identity, ownership, and the existing fund detail flow.

### Approach B: Separate public templates

Create a second template model detached from user funds. Rejected because publishing would duplicate basket data and create synchronization and ownership rules before they are needed.

### Approach C: Share-link-only copying

Allow copying only from a direct public URL and omit the leaderboard. Rejected because it helps Yann's X post but does not solve discovery inside OhMyFund.

## Recommended Approach

Extend the current `funds` model and keep the feature narrow.

### Data model

- Add `published_at`, nullable. `NULL` means private.
- Add `public_id uuid UNIQUE`, generated on first publication. It never changes, is retained through unpublish/republish, and is never reused.
- Add `publisher_name varchar(40)`, scoped to the published fund. Normalize to Unicode NFC, trim, require 1–40 characters, reject control characters, and escape it as text when rendered. Do not expose the wallet address as creator identity.
- Add `copy_count bigint NOT NULL DEFAULT 0` to `funds`, updated only inside a successful copy transaction. Index public funds by `(copy_count DESC, published_at ASC, id ASC)`.
- Add an immutable `fund_copy_events` table with `source_fund_id`, `source_public_id`, `source_version`, `copied_fund_id`, `copying_user_id`, `idempotency_key`, `request_hash`, and `created_at`. `source_version` is the existing positive integer `funds.version`, incremented by every basket replacement. Use `ON DELETE SET NULL` for both fund references so historical popularity survives a later fund-deletion feature. Account deletion does not exist; its future design must define any required event anonymization before adding that capability.
- Enforce `UNIQUE(copying_user_id, idempotency_key)` and `UNIQUE(source_fund_id, copying_user_id)`. The copy event, not surviving copied-fund lineage, is the durable definition of a successful copy. The owner cannot copy their own public fund. Each other user can create one copy of a source; later attempts return the existing copied fund and do not change rank.
- The event-to-copied-fund reference is sufficient for traceability; do not add a reverse event reference to `funds`. A copied fund remains private. If its owner later publishes it, copies count for that newly published fund only, not for the original source.
- Unpublishing sets `published_at` to `NULL` and removes the fund from public reads without altering existing copies. Republishing preserves `public_id` and assigns a new `published_at` time.
- Editing a published source changes what future copies receive. Existing copies remain unchanged.
- Fund and account deletion do not exist in the current product and remain out of scope. A future deletion design must unpublish first and preserve anonymized copy events and counts.

### API

- `GET /api/public/funds`: anonymous top 50 leaderboard ordered by copy count descending, publication time ascending, then fund ID ascending. Pagination is deferred until more than 50 public funds exist.
- `GET /api/public/funds/:publicId`: anonymous source fund detail.
- `POST /api/funds/:id/publish`: authenticated owner upsert with `publisherName`. First publication returns `201`, creates `public_id`, and sets `published_at`. Calling it on an already published fund returns `200` and updates only the public name without rotating the ID or publication time.
- `DELETE /api/funds/:id/publish`: authenticated owner action that unpublishes without deleting the fund.
- `POST /api/public/funds/:publicId/copy`: authenticated atomic operation with `name` in the body and `Idempotency-Key: <uuid>` in the header.
- Apply existing host, origin, CSRF, session, catalog-pair, mint-uniqueness, asset-count, and 100% weight validation rules to the new boundaries.

Public endpoints use dedicated allowlisted response contracts. The list returns only `rank`, `publicId`, `fundName`, `publisherName`, the top three assets, `assetCount`, `copyCount`, and `basketUpdatedAt`. Each top asset contains `assetId`, `variantId`, `symbol`, and `weightBps`. Detail returns `publicId`, `fundName`, `publisherName`, `assetCount`, `copyCount`, `basketUpdatedAt`, and allocation rows containing only `assetId`, `variantId`, `symbol`, catalogue `name`, optional `issuer`, and `weightBps`. Detail allocation is ordered by weight descending, then `assetId` ascending, and does not include query-relative rank. Neither endpoint serializes the private fund object, owner ID, wallet address, holdings, balances, plans, activity, or copy lineage.

`basketUpdatedAt` comes from the existing `funds.updated_at`, which changes only in the explicit basket-replacement SQL. This repo uses raw SQL and has no automatic timestamp hook or trigger. Publish, unpublish, public-name changes, and copy-count increments must omit `updated_at` from their `UPDATE` statements. Top assets are ordered by weight descending, then `asset_id` ascending; the list returns three and shows `+N` when more exist. `rank` is computed from the current top-50 query and may move between requests as successful copies arrive.

Publish succeeds only when the owned fund still has 2–8 distinct, currently approved catalogue selections, distinct mints, positive weights totaling 10,000 basis points, and a valid publisher name. A later catalogue retirement leaves public detail readable but disables copying until the basket becomes valid again.

Copy first looks up a completed event for the authenticated user and idempotency key. A matching request replays its original fund even if the source is now unpublished or invalid. A hash mismatch returns `409 IDEMPOTENCY_CONFLICT`. It then checks for an existing event for that user and `source_public_id`; a different-key repeat returns the existing copied fund even if the source is now unpublished. With no event, the server begins one PostgreSQL transaction, finds and locks the source fund row by `public_id` with `FOR UPDATE`, then repeats both checks in the same order: idempotency key first, prior user/source copy second. Those post-lock checks catch an event that committed while this request waited. Only then does it confirm the source is public, reject self-copy, read and validate the committed asset set, create the private fund and assets, write its creation activity, write the copy event, increment `copy_count`, commit, and return the new fund plus `sourceVersion = funds.version`. Fund edits use the same row lock, so the copy receives either the complete version before an edit or the complete version after it, never a mixed basket.

The client generates one UUID idempotency key when the user submits. The server stores it permanently with a hash of `publicId + trimmed name`. Replaying the same user, key, and hash returns the original successful fund. Reusing the key with a different request returns `409 IDEMPOTENCY_CONFLICT`. No key means `400 VALIDATION`. If two requests with the same key race, the source row lock lets one transaction commit first; the second request's post-lock idempotency re-check loads and returns that committed response. The unique constraint remains a final backstop. This race requires an integration test.

The `FOR UPDATE` lock serializes edits and copies of the same source fund. That is an accepted first-release tradeoff. Revisit the counter and snapshot strategy only if a public fund receives enough concurrent copies to create measurable latency.

### Product flow

1. A fund owner chooses Publish from fund detail and confirms that the target allocation will become public.
2. The public Leaderboard shows compact rows: rank, fund name, creator, top assets, copy count, and Copy.
3. Selecting the fund name opens its public detail. Copy stays directly available in the row.
4. A signed-in user sees the naming dialog. It asks only for the new fund name and explains that the result is an independent snapshot.
5. For a signed-out user, Copy first stores only `publicId` in `sessionStorage` with a 15-minute timestamp, starts the existing same-tab Turnkey login, then opens the naming dialog after the session binds. No entered name exists before authentication.
6. A successful copy opens the new private fund in the user's portfolio.
7. The fund page offers the existing optional draft recurring-buy flow.

### States and edge cases

- Empty leaderboard: explain that no funds are public yet. Never expose private funds.
- Source unpublished between list and copy: return `404 NOT_FOUND` and keep the entered fund name in the dialog.
- Source edited between list and copy: the shared row lock copies one complete committed version and returns `sourceVersion`.
- Duplicate requested fund names are allowed, matching the current schema and create-fund behavior. Never overwrite an existing fund.
- Asset retired from the current catalogue: keep public detail readable; return `409 ASSET_UNAVAILABLE` with the unavailable asset IDs and keep the dialog state.
- Copy request retried after a timeout with the same idempotency key: replay the original successful response. A changed request with that key returns `409 IDEMPOTENCY_CONFLICT`.
- Owner attempts to copy their own fund: return `409 SELF_COPY` without creating an event or changing the count.
- User attempts a second deliberate copy with a new idempotency key: return the existing copied fund with `alreadyCopied: true`; do not create another fund or increment the count, even when the source has since been unpublished.
- Expired or missing signed-out intent: return to the leaderboard without opening a stale dialog.
- Long fund or creator names: truncate in the list and show the full value on detail.
- Copy count updates only after the copy transaction succeeds.

Stable API errors are: `401 UNAUTHENTICATED`, `403 FORBIDDEN` for a non-owner publish action, `404 NOT_FOUND` for a missing or unpublished public ID, `400 VALIDATION` for invalid names, publication state, or missing idempotency key, `409 ASSET_UNAVAILABLE`, `409 IDEMPOTENCY_CONFLICT`, `409 SELF_COPY`, and `503 TEMPORARY_UNAVAILABLE` for rollback-safe infrastructure failure. A repeat copy by the same non-owner is a successful replay of their existing copied fund, not an error.

## Open Questions

- None block implementation. Pagination becomes necessary when the public fund count approaches the fixed top-50 response limit.

## Success Criteria

- A private fund never appears in anonymous public responses.
- An owner can publish and unpublish without changing the private fund's basket or plans.
- A visitor can browse the leaderboard without signing in.
- An authenticated user can copy a published fund in one atomic action.
- The copied fund contains the exact source assets and weights at copy time and none of the source holdings, activity, or plans.
- Later source edits do not change the copied fund.
- A failed copy transaction creates no fund, event, or count change. Replaying a submitted request with its original idempotency key returns the same fund without duplication.
- Self-copy does not count. A source's copy count equals the number of distinct non-owner users with a committed copy event and does not fall when a copied fund is later removed by a future deletion feature.
- After copy, the user reaches the new fund and can create an optional draft recurring buy.
- Mobile and desktop views match the approved compact-list preview with no horizontal overflow.

## Dependencies

- Existing fund CRUD and validation in the API.
- Existing session, CSRF, host, and origin protections.
- Existing public catalog identity lookup.
- Existing fund detail and draft recurring-buy flow.
- A migration for public fund fields, the append-only copy event, indexes, and new public API contracts.
